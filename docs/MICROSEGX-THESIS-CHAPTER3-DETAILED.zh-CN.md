## 3.1 功能需求分析

### 3.1.1 需求背景

Kubernetes 集群中的应用通常由多个 Pod、Service、Ingress、NodePort、控制组件和第三方安全组件共同组成。与传统单机服务相比，容器集群的网络访问关系具有以下特点：

1. 访问关系动态变化
   - Pod 会随着调度、扩缩容、重启不断变化。
   - 单纯依靠固定 IP 编写访问控制规则不可靠。
   - 规则对象应尽量面向工作负载、命名空间、业务组或自动归类后的工作负载组。

2. 东西向通信复杂
   - 前端、后端、数据库、缓存、定时任务、安全组件之间存在大量内部通信。
   - 如果完全依赖人工维护微隔离策略，容易遗漏必要访问关系，也容易保留过期规则。

3. 南北向暴露面难治理
   - Kubernetes 中常见的 Service、NodePort、Ingress、HostPort、LoadBalancer 等机制都可能形成外部访问入口。
   - 这些入口如果缺少统一归因，运维人员很难判断某个开放端口属于哪个服务、哪个命名空间、哪个业务系统。

4. 传统逐连接学习容易误学习
   - 原系统收到一条连接后就可能立即生成 learned allow 规则。
   - 临时调试流量、扫描流量、异常探测流量也可能被固化为允许规则。
   - 长期运行后规则数量不断增长，且很多规则已经不再对应真实 Pod 或业务。

5. 零信任访问与普通访问需要区分
   - 通过 OpenZiti 代理访问业务服务时，访问路径和普通 Ingress/NodePort 访问不同。
   - 如果学习阶段无法区分零信任链路和普通链路，后续规则管理、实验分析和论文指标都会混在一起。
   - 因此系统必须在学习之前完成流量归因，将 `ziti-router -> 业务工作负载` 这类链路识别为零信任访问链路。

基于以上背景，本项目的功能需求可以归纳为：

> 在尽量复用 MicroSegX/NeuVector 既有 controller、agent/enforcer、策略编译与数据面执行链路的基础上，构建一套覆盖内部微隔离策略自动生成、外部端口暴露面治理和零信任访问控制的云主机微隔离系统。

### 3.1.2 用户角色与使用场景

论文中可以定义三个主要角色：

1. 集群管理员
   - 关注集群整体安全状态、组件运行状态、开放端口、自动策略模式和部署结果。
   - 需要知道系统当前是在观察、学习还是执行策略。

2. 安全运维人员
   - 关注哪些通信已经被学习成规则，哪些规则疑似失效，哪些链路属于异常访问。
   - 需要批量删除无效规则、人工调整规则类别、配置周期规则。

3. 业务负责人
   - 关注某个命名空间或业务应用的访问关系。
   - 需要按命名空间、工作负载、业务名、流量来源筛选规则和观察流量。

典型使用场景：

1. 新业务上线
   - 系统先进入观察或学习状态。
   - 业务稳定通信被聚合为候选特征。
   - 达到阈值后生成基线允许规则。

2. 定时任务访问数据库
   - 流量只在每天某个固定时间段出现。
   - 系统通过时间槽分布判断其周期性。
   - 生成时间约束允许规则，只在对应时间段生效。

3. 异常扫描或多端口探测
   - 同一来源短时间访问多个端口或多个目标。
   - 系统根据端口爆发、目标爆发、威胁事件、违反状态等信号计算异常分数。
   - 高置信异常生成临时拒绝规则，并通过 TTL 自动过期。

4. 业务对外暴露治理
   - port-audit 发现某个服务通过 NodePort 或 Ingress 暴露。
   - 页面展示暴露端口、命名空间、服务、工作负载。
   - 运维人员可以选择将访问入口收敛到 OpenZiti 零信任访问路径。

5. 零信任访问链路学习
   - 外部用户通过 OpenZiti identity 访问某个 service。
   - OpenZiti router 在集群内部代理到业务 Pod。
   - 系统将这条链路识别为 `zero_trust` 来源，而不是普通入口流量。
   - 规则学习、展示和筛选均可区分零信任链路和普通链路。

### 3.1.5 功能边界

论文中需要明确边界，避免过度表述：

1. 本文不是重新设计数据面
   - 系统复用原有策略编译和下发链路。
   - 创新点在 controller 侧自动学习、分类、规则生命周期和可视化治理。

2. 本文不是完整机器学习异常检测系统
   - anomaly deny 使用启发式评分。
   - 其优点是实现简单、可解释、适合本科系统实现论文。

3. 本文不解决多 controller 候选状态同步
   - 第一版候选特征保存在 controller 内存中。
   - 正式规则和 metadata 会落 KV。

4. 零信任不等于自动关闭所有普通入口
   - 系统可以区分零信任链路与普通入口链路。
   - 是否关闭普通入口属于运维策略，不应写成系统自动完成所有暴露面消除。

## 3.2 技术方案设计

### 3.2.1 系统架构设计

#### 3.2.1.1 总体设计思想

本系统采用“低侵入改造 + 自动策略增强 + 外部访问治理”的设计思想。

核心原则如下：

1. 保留原有执行链路
   - 原系统已经具备完整的策略编译、agent 下发和数据面执行能力。
   - 因此不重新实现网络拦截，而是在 controller 侧增强策略生成逻辑。

2. 将逐连接学习改为窗口聚合学习
   - 原系统看到连接后可能立即生成 learned rule。
   - 新系统先将连接放入观察窗口，再聚合同类通信行为，最后基于统计特征判断是否生成规则。

3. 使用“两层规则模型”
   - 第一层是规则本体，继续使用 `CLUSPolicyRule`。
   - 第二层是自动规则元数据，记录分类、置信度、周期槽、TTL、原因码等信息。

4. 以分类元数据控制编译优先级
   - 自动规则本体仍属于 learned 类型，但运行时不按旧 learned 规则直接处理。
   - 编译阶段根据 metadata 将规则分为 anomaly、periodic、baseline 等桶，按固定顺序注入运行时策略。

5. 在学习前完成流量归因
   - 对 ServiceIP、WorkloadIP、Ingress、OpenZiti router 等来源进行规范化。
   - 尽量把规则对象归到实际工作负载组，而不是 IP。
   - 对零信任流量单独标记为 `zero_trust`，与普通入口访问分开学习和展示。

6. 允许人工干预
   - 自动学习不是完全不可控的黑盒。
   - 运维人员可以新增规则、修改规则类型、配置周期时间段、删除或批量删除规则。

#### 3.2.1.2 自动策略运行模式

系统提供三种模式，论文中建议翻译为“兼容模式、观察模式、执行模式”：

| 模式 | 英文值 | 行为 | 适用阶段 |
|---|---|---|---|
| 兼容模式 | legacy | 保持原有 learned 行为 | 回滚、对照实验 |
| 观察模式 | shadow | 观察流量并计算候选，但不自动写规则 | 调参、验证误报率 |
| 执行模式 | enforce | 自动生成、更新、删除规则并参与策略编译 | 正式验证自动策略效果 |

需要注意：

- shadow 模式下可以看到候选特征、分数和待生成类别，但不会真正产生自动 allow/deny 规则。
- enforce 模式下，自动规则会写入 policy store，并在编译阶段参与运行时策略。
- 用户手动创建的规则仍然可以作为人工干预存在。
- 为避免旧规则干扰自动策略实验，自动模式下 legacy learned 规则不作为核心运行时依据；论文中可以写成“新策略体系以自动规则和用户规则为主，旧 learned 作为兼容路径保留”。

#### 3.2.1.3 自动策略数据模型

系统使用两层数据模型。

第一层：规则本体

```text
CLUSPolicyRule
  - From
  - To
  - Ports / Applications
  - Action: allow 或 deny
  - CfgType: Learned
  - MatchCntr / LastMatchAt
```

这层用于复用原有策略编译和下发链路。

第二层：自动规则元数据

```text
CLUSAutoPolicyMeta
  - RuleID
  - Class: baseline / periodic / anomaly
  - Confidence
  - CreatedAt
  - LastObserved
  - ExpiresAt
  - PeriodicSlots
  - ReasonCodes
```

这层用于表达自动规则的语义。

为什么要这样设计：

1. 如果新增全新的 `CfgType`，会影响 REST、排序、rule head、缓存、同步和编译逻辑，改动面过大。
2. 复用 `CLUSPolicyRule` 可以保持 agent 和数据面协议不变。
3. metadata 可以承载周期、TTL、置信度、原因码等新信息。
4. 编译阶段可以根据 metadata 控制运行时优先级。

#### 3.2.1.4 自动策略学习流程

自动策略学习流程可以写成：

```text
连接事件上报
  -> 端点归一化
  -> 流量来源识别
  -> 写入观察窗口
  -> 周期性 drain 观察窗口
  -> 聚合为候选特征
  -> 更新历史特征状态
  -> 计算 baseline / periodic / anomaly 分数
  -> 生成候选决策
  -> shadow 模式只展示
  -> enforce 模式写入规则和 metadata
  -> 策略编译并下发
```

一个候选特征可以理解为：

```text
Feature = (FromGroup, ToGroup, Protocol, Application?)
```

如果不是应用识别流量，则进一步收集端口集合：

```text
Ports = { tcp/80, tcp/443, tcp/8080 ... }
```

这样做的原因是：

- 不把每一条连接直接变成规则。
- 同一组对下多个端口可以进行去重和范围归并。
- 可避免端口数量过多时直接退化为 `any`。

#### 3.2.1.5 端点归因与 ServiceIP 处理

论文中建议强调：策略学习不应该以临时 IP 作为主要对象。

系统会尽量将以下对象归一化：

1. Workload IP
   - 如果连接中出现 `Workload:<hash>` 或临时 workload IP，系统根据当前 workload cache 解析到真实工作负载组。

2. Service IP
   - 如果连接目标是 `nv.ip.xxx` 形式的 ServiceIP 组，系统不会直接学习成 ServiceIP 规则。
   - 系统会尝试根据 Service 名称、命名空间、selector label 或当前存活 workload 反查后端工作负载组。
   - 无法归因的 ServiceIP 特征会被过滤，避免生成不可运维的 IP 规则。

3. OpenZiti router
   - 如果来源组属于 ziti-router/openziti 命名空间，则标记为 zero_trust 链路。
   - 这意味着同样访问 `nv.nginx.web`，普通 Ingress 链路和 `ziti-router -> nv.nginx.web` 会被分开统计、分开学习、分开展示。

4. port-audit 扫描节点
   - port-audit 对 node scope 的扫描可能产生大量端口。
   - 系统会过滤 `k8s-port-audit -> nodes` 这类扫描型流量，避免它被误学成业务访问规则。

#### 3.2.1.6 三类规则分类算法

##### baseline allow

baseline allow 用于描述长期稳定、重复出现、风险较低的业务通信。

使用的特征包括：

- 连续观察窗口数。
- 保留期内命中窗口总数。
- 观察周期数。
- 源工作负载覆盖率。
- 异常风险的反向指标。

公式：

```text
S_baseline =
  0.30 * f_consecutive +
  0.25 * f_total +
  0.20 * f_days +
  0.15 * f_srccov +
  0.10 * f_safe
```

其中：

```text
f_consecutive = min(ConsecutiveWindows / 6, 1)
f_total       = min(TotalWindows / 12, 1)
f_days        = min(DistinctDays / 3, 1)
f_srccov      = min(SourceWorkloadSeen / SourceGroupSize, 1)
f_safe        = 1 - S_anomaly
```

promotion 条件：

```text
DistinctDays >= 3
S_baseline >= 0.75
S_anomaly <= 0.30
```

论文表述：

> 基线允许规则并不是简单地把一次连接加入白名单，而是要求通信在多个观察窗口和观察周期中重复出现，并且不存在明显异常信号。

##### periodic allow

periodic allow 用于描述固定时间段出现的正常通信，例如备份任务、CronJob、定时报表。

系统将一周划分为多个时间槽。生产语义下推荐每 30 分钟一个槽：

```text
一周槽数 = 7 * 24 * 60 / 30 = 336
```

若第 `i` 个槽的命中次数为 `c_i`，则：

```text
p_i = c_i / Σ c_i
H = -Σ(p_i * log(p_i))
S_concentration = 1 - H / log(N)
```

其中：

- `H` 是时间分布熵。
- `N` 是总槽数。
- 流量越集中在少数槽，熵越低，`S_concentration` 越高。

最终周期分数：

```text
S_periodic =
  0.45 * S_concentration +
  0.25 * f_days +
  0.20 * f_repeat +
  0.10 * f_outside
```

promotion 条件：

```text
DistinctDays >= 7
S_periodic >= 0.70
PeriodicSlots 不为空
S_baseline < 0.85 或 S_periodic > S_baseline
```

运行时生效方式：

- 如果当前时间位于 `PeriodicSlots`，规则参与策略编译。
- 如果当前时间不在 `PeriodicSlots`，规则不注入运行时策略。

论文中要注意：

- 不建议把周期槽解释成“第 1 分钟、第 2 分钟”。
- 正式论文应按自然时间解释，例如“周一 08:00-17:00、周日 19:00-20:00”。
- 实验加速只是测试手段，不应作为正式方法的唯一表达。

##### anomaly deny

anomaly deny 用于描述高风险异常通信。

系统使用启发式威胁行为识别，不是黑盒机器学习。

公式：

```text
S_anomaly =
  0.25 * f_novelty +
  0.20 * f_portburst +
  0.20 * f_dstburst +
  0.15 * f_time_deviation +
  0.20 * f_violation
```

含义：

- `f_novelty`：新出现的通信关系风险更高。
- `f_portburst`：同一来源短时间访问多个端口风险更高。
- `f_dstburst`：同一来源短时间访问多个目标风险更高。
- `f_time_deviation`：出现在历史上少见时间槽的流量风险更高。
- `f_violation`：伴随策略违反、ThreatID、Severity 的流量风险更高。

promotion 条件：

```text
S_anomaly >= 0.80
或 ThreatID 存在且 Severity 较高
```

规则特点：

- `Action = deny`
- 带 TTL
- 到期后自动清理
- 避免一次误判造成永久阻断

#### 3.2.1.7 零信任链路快速准入

零信任访问与普通入口访问不同。OpenZiti 本身已经通过 identity、service policy、edge router policy 等机制完成身份和服务授权，因此 `ziti-router -> 业务工作负载` 这类链路可以被视为受控入口链路。

系统对零信任链路做了单独归因：

```text
普通入口链路:
  Workload:ingress -> nv.nginx.web

零信任链路:
  nv.ziti-router.openziti -> nv.nginx.web
```

这两类链路在学习阶段即被分开，而不是生成规则后再区分。

对于低风险零信任链路，系统可以降低基线准入门槛：

```text
如果 TrafficSource = zero_trust
且 S_anomaly < 0.80
则可快速形成 baseline allow 候选
```

论文中可以解释为：

> 由于零信任链路已经经过外部身份认证和服务授权，系统在微隔离策略学习时将其作为独立受控来源处理。这样既不会把普通入口流量和零信任代理流量混在一起，也便于后续分别统计和管理。

#### 3.2.1.8 策略编译与生效顺序

自动规则最终仍然需要进入运行时策略。

系统采用稳定分桶编译：

```text
Federal
  -> Ground
  -> auto anomaly deny
  -> UserCreated
  -> auto periodic allow
  -> auto baseline allow
  -> legacy learned
```

实际工程中还保留了可选的系统保活/保护规则开关，但论文主线不建议把它作为核心创新点。

关键点：

1. `rules[0]` 默认地址表不改变。
2. anomaly deny 优先级高于 allow。
3. 用户手动规则高于自动 allow，便于人工兜底。
4. periodic allow 只在当前时间槽激活时编译。
5. baseline allow 用于日常稳定通信。
6. 自动模式下，旧 learned 不再作为主要运行时依据。

#### 3.2.1.9 生命周期管理

系统提供三类生命周期管理：

1. anomaly deny TTL
   - 异常拒绝规则创建时写入 `ExpiresAt`。
   - TTL ticker 到期删除。

2. baseline/periodic 老化
   - 根据 `LastMatchAt`、`MatchCntr`、两端 endpoint 是否仍存在进行判断。
   - 长期无命中或两端无活跃 workload 的规则可标记为疑似失效。

3. 人工清理
   - 页面支持单条删除和多选删除。
   - 对疑似失效规则可以筛选后统一处理。

### 3.2.2 核心技术选型

#### 3.2.2.1 Kubernetes

选型原因：

- Kubernetes 是当前云主机和容器云场景的主流基础设施。
- Pod、Service、Ingress、Namespace 等对象天然适合作为微隔离系统的资源归因对象。
- 系统可以通过 Kubernetes 部署 controller、manager、enforcer、scanner、OpenZiti 和 port-audit。

论文表述：

> 本文以 Kubernetes 集群作为系统运行环境，通过命名空间、工作负载、服务和入口资源描述业务对象和访问路径，为后续策略学习和暴露面治理提供统一资源模型。

#### 3.2.2.2 MicroSegX/NeuVector

选型原因：

- 原系统已经具备成熟的连接事件采集能力。
- 原系统已有策略编译和数据面下发链路。
- 原 learned rule 机制提供了二次开发基础。
- 使用真实开源系统改造比从零写 demo 更具工程价值。

论文表述：

> 本文基于 MicroSegX/NeuVector 既有架构进行二次开发，将研究重点放在策略自动生成和生命周期治理，而不是重新实现底层数据面。

#### 3.2.2.3 Go Controller

选型原因：

- controller 原有主体使用 Go 实现。
- Go 适合高并发控制面逻辑和 Kubernetes 环境部署。
- 自动策略引擎需要定时器、锁、KV 事务和缓存管理，适合在 controller/cache 层实现。

#### 3.2.2.4 KV Store 与事务

选型原因：

- 原策略规则已经通过 KV 存储和同步。
- 自动规则本体与 metadata 必须原子写入或删除。
- 使用原有 `CLUSLockPolicyKey` 和事务机制可以避免与 REST 修改、旧 learned 写入冲突。

论文表述：

> 自动规则本体与元数据采用事务方式共同写入，保证运行时编译、页面展示和生命周期清理的一致性。

#### 3.2.2.5 OpenZiti

选型原因：

- OpenZiti 提供 identity、service、policy、router、terminator 等零信任访问控制能力。
- 可以将原本直接暴露的服务转换为经过身份认证和授权的受控访问路径。
- 与 Kubernetes 内部服务结合后，可以形成“端口暴露发现 -> 零信任发布 -> 零信任链路学习”的闭环。

论文表述：

> 本文不重新实现零信任协议，而是集成 OpenZiti 作为外部访问控制基础，并将其访问链路纳入 MicroSegX 自动策略学习体系。

#### 3.2.2.6 k8s-port-audit

选型原因：

- Kubernetes 暴露面分布在 Service、Ingress、NodePort、HostPort 等对象中。
- port-audit 可将开放端口与命名空间、服务、工作负载对应起来。
- 该模块为外部访问面治理提供数据基础。

#### 3.2.2.7 Angular/Web 前端

选型原因：

- 原 manager 前端已经使用 Angular。
- 自动策略和零信任管理需要较强的交互式页面，包括筛选、分页、弹窗编辑、详情抽屉。
- 继续沿用现有前端技术栈可降低集成成本。

## 3.3 核心功能模块实现

### 3.3.1 云主机安全防护模块

这里的“云主机安全防护模块”建议写成覆盖两类能力：

1. 集群内部运行时防护
   - 连接事件采集。
   - 微隔离策略学习和执行。
   - 异常拒绝和规则生命周期。

2. 集群外部暴露面防护
   - 开放端口扫描。
   - 暴露资源归因。
   - 零信任入口辅助治理。

#### 3.3.1.1 模块目标

该模块的目标是：

> 对 Kubernetes 集群中运行的工作负载和服务入口进行持续观察，识别内部访问关系和外部暴露入口，并通过自动策略和可视化治理降低非必要网络暴露。

具体目标：

- 识别哪些工作负载之间存在访问关系。
- 识别哪些访问关系稳定、周期或异常。
- 发现 Service/Ingress/NodePort/HostPort 等对外暴露入口。
- 帮助运维人员判断哪些入口应保留、收敛或改造为零信任入口。
- 通过规则命中、失效状态、生命周期管理避免策略长期失控。

#### 3.3.1.2 连接事件采集与防护执行

系统复用 MicroSegX 原有 enforcer/agent 能力：

```text
业务 Pod 产生连接
  -> enforcer 观察连接
  -> controller 接收 CLUSConnection
  -> controller 更新网络活动图
  -> 自动策略 observer 接收同一连接
  -> 策略编译后再下发 enforcer
  -> enforcer 数据面执行 allow/deny
```

这一设计的优势：

- 不需要重新实现流量采集。
- 不需要修改 agent 协议。
- 不需要改变数据面匹配方式。
- 可以直接使用原有策略命中统计。

#### 3.3.1.3 自动策略观察与候选特征

模块将连接事件转化为候选特征。

候选特征记录：

- 源组。
- 目标组。
- 协议。
- 应用 ID。
- 端口集合。
- FQDN 集合。
- 源 workload 集合。
- 首次观察时间。
- 最近观察时间。
- 连续窗口数。
- 历史窗口数。
- 观察周期数。
- 时间槽命中情况。
- 异常信号。

页面上的一些指标可以这样解释：

| 页面字段 | 论文解释 |
|---|---|
| 连续观察窗口 | 该特征最近连续出现了多少个观察窗口 |
| 保留期内命中窗口 | 在候选特征保留期内，该通信出现过多少个不同观察窗口 |
| 观察周期数 | 该通信跨越了多少个统计周期，生产语义可理解为天 |
| 源工作负载覆盖率 | 源组内有多少比例的 workload 产生过该通信 |
| 活跃槽 | 该通信出现过的时间槽，用于周期性判断 |
| 基线分数 | 稳定业务通信的置信程度 |
| 周期分数 | 固定时间出现的置信程度 |
| 异常分数 | 风险行为的置信程度 |

#### 3.3.1.4 异常拒绝与临时封禁

云主机安全防护不能只生成 allow，也需要处理明显异常行为。

anomaly deny 主要用于：

- 多端口扫描。
- 多目标爆发访问。
- 首次出现的高风险访问。
- 携带 ThreatID 或高 Severity 的连接。
- 出现在异常时间槽的连接。

规则特点：

- action 为 deny。
- metadata class 为 anomaly。
- 默认带 TTL。
- TTL 到期后自动删除。

论文中可以写：

> 为降低误封风险，异常拒绝规则不作为永久黑名单，而是采用带过期时间的临时拒绝策略。

#### 3.3.1.5 端口暴露面扫描与归因

端口暴露治理模块关注南北向访问。

扫描对象包括：

- Service。
- NodePort。
- Ingress。
- HostPort。
- LoadBalancer。
- 节点监听端口。

归因信息包括：

- 命名空间。
- 服务名称。
- 工作负载名称。
- 端口。
- 协议。
- 暴露类型。
- 是否存在零信任发布路径。

页面用途：

- 让运维人员知道哪些服务正在暴露。
- 判断暴露入口是否合理。
- 与 OpenZiti 管理区联动，发布零信任服务。

论文中可以写：

> 端口暴露面治理模块并不直接替代 Kubernetes Service 机制，而是对已有暴露入口进行统一发现、归因和展示，为后续访问入口收敛提供依据。

#### 3.3.1.6 规则失效识别

系统支持识别疑似失效规则。

判断依据包括：

- 规则源组是否仍有存活 endpoint。
- 规则目标组是否仍有存活 endpoint。
- 规则是否长期未命中。
- 规则是否引用了无法归因的 ServiceIP 或已消失工作负载。

页面上可以根据“疑似失效”筛选后批量删除。

论文中建议写：

> 规则失效识别用于缓解自动学习系统长期运行后规则膨胀的问题。系统通过端点存活状态和命中统计辅助判断规则是否仍有实际业务意义。

#### 3.3.1.7 云主机安全防护模块小结

本模块形成的闭环是：

```text
流量观察
  -> 风险与稳定性判断
  -> 自动策略生成
  -> 数据面执行
  -> 命中统计与失效识别
  -> 自动或人工回收
```

该闭环体现了“观察、生成、执行、反馈、回收”的安全防护思路。

### 3.3.2 多云工作负载访问控制模块

这个小节建议重点写“工作负载之间如何访问控制”，而不是只写 OpenZiti。

可以将其定义为：

> 多云工作负载访问控制模块面向不同命名空间、不同业务组以及可能跨集群/跨网络入口的工作负载访问关系，提供基于自动策略、手动策略和零信任入口的统一访问控制能力。

#### 3.3.2.1 模块目标

模块目标：

- 将访问控制对象从 IP 提升到工作负载组、命名空间和业务语义。
- 区分普通入口、零信任入口、系统组件通信和直接内部通信。
- 支持自动生成规则，也支持人工编辑规则。
- 支持规则按时间段生效。
- 支持异常访问拒绝。

#### 3.3.2.2 流量来源分类

系统将流量来源分成四类：

| 类型 | 含义 | 示例 |
|---|---|---|
| direct | 普通东西向工作负载通信 | `nv.client.learn -> nv.backend.learn` |
| ingress | 传统入口流量 | `Workload:ingress -> nv.nginx.web` |
| zero_trust | OpenZiti 代理访问链路 | `nv.ziti-router.openziti -> nv.nginx.web` |
| system | 系统组件或控制面通信 | `nv.manager.microsegx -> nv.controller.microsegx` |

这样设计的原因：

- 普通访问和零信任访问的安全语义不同。
- 同一目标服务可能同时存在普通入口和零信任入口。
- 如果不区分，无法证明“零信任链路被单独学习和管理”。
- 前端筛选和实验指标也需要按来源拆分。

#### 3.3.2.3 零信任访问控制实现

OpenZiti 部分包含以下对象：

- controller：负责身份、服务和策略管理。
- router：负责承载边缘会话和代理流量。
- identity：访问主体身份。
- service：被发布的业务服务。
- service policy：控制哪些 identity 可以 dial/bind 服务。
- edge router policy：控制 identity 或 router 可以使用哪些 edge router。
- terminator：将 Ziti service 连接到实际后端服务。

访问链路：

```text
用户 identity
  -> OpenZiti controller 获取授权
  -> OpenZiti router 建立会话
  -> router 连接 Kubernetes 内部业务服务
  -> MicroSegX enforcer 观察 router 到业务 Pod 的连接
  -> 自动策略将其标记为 zero_trust
```

论文中可以强调：

> 系统并不是只提供一个 OpenZiti 管理页面，而是将 OpenZiti 产生的实际业务访问链路纳入自动策略学习过程，从而实现零信任访问路径与微隔离策略的联动。

#### 3.3.2.4 自动规则如何真正控制访问

规则生成后，访问控制并不是停留在页面显示。

生效路径：

```text
自动规则 / 手动规则
  -> policy store
  -> policyCache
  -> 编译分桶
  -> CLUSGroupIPPolicy
  -> agent/enforcer
  -> 数据面匹配
```

规则动作：

- baseline allow：允许稳定通信。
- periodic allow：仅在指定时间段允许。
- anomaly deny：拒绝异常通信。
- user rule：人工规则，优先于自动 allow。

规则优先级：

```text
平台规则
  -> 基础规则
  -> 异常拒绝
  -> 用户规则
  -> 周期允许
  -> 基线允许
```

解释：

- deny 要在 allow 前面，避免异常流量被基线规则放行。
- 用户规则高于自动 allow，便于人工修正。
- 周期规则比基线规则更具体。

#### 3.3.2.5 周期性访问控制

周期规则的运维表达应使用自然时间：

```text
周一 08:00-17:00
周二 08:00-17:00
周日 19:00-20:00
```

而不是：

```text
第 1 个实验周期
第 2 个实验周期
```

系统内部可以用 slot 编码，但页面和论文中应解释为自然时间段。

如果需要表达多个时间段：

```text
周期规则 = 多个时间段集合
时间段 = 星期集合 + 开始时间 + 结束时间
```

例如：

```text
{周一, 周二} 08:00-17:00
{周日} 19:00-20:00
```

系统将这些时间段转换为对应的 `PeriodicSlots`。

#### 3.3.2.6 人工编辑与新增规则

为了避免自动策略成为不可控黑盒，系统提供人工介入：

1. 新增规则
   - 选择源工作负载组。
   - 选择目标工作负载组。
   - 选择规则类型。
   - 配置端口或应用。
   - 如果是周期规则，配置自然时间段。
   - 如果是异常拒绝，配置 TTL。

2. 修改规则
   - baseline 可以转为 periodic。
   - baseline 可以转为 anomaly deny。
   - anomaly deny 可以转为 allow。
   - 修改后 metadata 中记录 `manual_override` 原因。

3. 删除规则
   - 支持单条删除。
   - 支持多选删除。
   - 支持筛选疑似失效后批量清理。

论文中可以写：

> 自动策略系统并不排斥人工运维，而是将自动学习结果作为初始策略建议，并提供人工确认、调整和清理能力。

#### 3.3.2.7 筛选与可观测能力

页面提供以下筛选维度：

- 命名空间。
- 工作负载或业务名称。
- 规则类型。
- 流量来源：direct / ingress / zero_trust / system。
- 是否疑似失效。
- 是否当前生效。
- 关键词搜索。

这样做的原因：

- 规则数量多时，需要快速定位某个业务。
- 零信任链路和普通入口链路必须分开查看。
- 已失效规则需要统一清理。
- 运维人员不能只看到 `from -> to`，还需要知道命名空间、业务、端口、状态和来源。

#### 3.3.2.8 多云工作负载访问控制模块小结

本模块的核心价值可以总结为：

```text
工作负载语义归因
  -> 流量来源分类
  -> 自动 / 手动规则生成
  -> 周期 / 异常访问控制
  -> 策略编译下发
  -> 页面化运维
```

论文中可以写：

> 多云工作负载访问控制模块将网络访问对象从传统 IP 和端口提升为工作负载、命名空间和业务链路，并进一步区分普通访问、入口访问和零信任访问，从而为动态云原生环境提供更可解释、更易运维的访问控制能力。

可以放在第 3 章末尾：

> 本章围绕 Kubernetes 场景下云主机微隔离系统的需求，分析了东西向通信自动策略生成、南北向端口暴露治理以及零信任访问控制三类核心需求。针对原系统逐连接即时学习易误学习、规则生命周期缺失、端口暴露难归因等问题，本文设计了基于观察窗口聚合的自动策略生成方案，在保留原有策略编译和数据面下发链路的基础上，引入自动规则元数据、三类评分算法、编译分桶优先级和规则生命周期管理机制。同时，系统结合 k8s-port-audit 与 OpenZiti，实现对外部暴露入口和零信任访问路径的统一展示与治理。通过将普通入口链路、零信任链路和工作负载内部通信在学习阶段即进行区分，系统能够为后续规则生成、策略执行和实验分析提供更清晰的语义基础。
