# MicroSegX 论文写作与图表使用建议

本文档只面向论文写作和答辩组织，用来把当前已经实现和调整过的 MicroSegX 项目整理成一条清晰、稳妥、可答辩的技术主线。

本文档不展开具体代码实现。

---

## 1. 当前项目应该如何定位

建议把整个项目统一表述为：

> 面向 Kubernetes 集群场景下的安全防护需求，设计并实现一套云主机微隔离系统。系统同时覆盖集群内部东西向通信控制和集群外部南北向访问控制，并围绕自动化策略生成、端口暴露面治理和零信任访问控制形成闭环。

这句话比“改了一个 NeuVector 模块”更适合本科论文，也比“发明一个全新安全平台”更稳妥。

当前项目可以拆成两个主板块：

1. 集群内部微隔离策略自动生成
   - 这是论文的核心创新板块。
   - 重点写自动观察、窗口聚合、特征评分、规则生成、策略编译和生命周期管理。

2. 集群外部暴露面治理与零信任访问控制
   - 这是系统落地板块。
   - 重点写端口暴露扫描、资源归因、开放入口收敛、OpenZiti 零信任接入和页面化管理。

建议论文里明确主次关系：

- 内部自动策略生成：主贡献。
- 外部暴露治理和零信任：配套系统能力。

## 2. 推荐论文题目

可选题目：

1. 基于 Kubernetes 的云主机微隔离系统设计与实现
2. 面向 Kubernetes 集群的自动化微隔离策略生成与零信任访问控制系统
3. 面向容器云环境的微隔离策略自动生成与暴露面治理系统设计

最稳妥推荐：

> 面向 Kubernetes 集群的云主机微隔离系统设计与实现

这个标题覆盖范围足够大，不会被“自动策略算法是否足够学术”卡住，也能容纳端口暴露和零信任部分。

## 3. 推荐章节结构

### 第 1 章 绪论

建议写：

- Kubernetes 在云主机场景中的普及。
- 集群内部东西向通信越来越复杂。
- 传统网络边界防护难以覆盖容器内部访问关系。
- 业务服务对外暴露容易造成端口暴露面扩大。
- 手工维护微隔离规则成本高、易出错、难持续。

本章贡献点可以写成：

- 设计并实现一套面向 Kubernetes 集群的云主机微隔离系统。
- 将原有逐连接即时学习机制改造为窗口聚合式自动策略生成机制。
- 基于稳定性、周期性和异常性将流量分类生成三类自动规则。
- 结合端口暴露扫描与零信任访问控制，实现外部访问面的收敛治理。
- 提供 Web 管理界面完成规则观察、生成、编辑、删除和部署验证。

### 第 2 章 相关技术

建议包含：

- Kubernetes 网络模型。
- 容器微隔离与东西向流量控制。
- NeuVector / MicroSegX 基本架构。
- 网络策略规则编译与数据面下发。
- OpenZiti 零信任网络。
- Kubernetes Service、Ingress、NodePort 与端口暴露面。

注意：

- 不要把 OpenZiti 写成本文发明的协议。
- 不要把 NeuVector 原有能力写成本文完全原创。

### 第 3 章 集群内部微隔离策略自动生成

这是核心章节，建议重点写。

推荐小节：

1. 原系统策略学习链路分析
   - enforcer 上报连接事件。
   - controller 接收 `CLUSConnection`。
   - 原系统 learned rule 通过逐连接即时学习生成。
   - 原有问题：偶发流量误学习、端口聚合粗、缺少生命周期、缺少周期/异常分类。

2. 自动策略总体设计
   - 连接事件不再直接生成规则。
   - 引入观察窗口。
   - 聚合同类通信行为。
   - 提取稳定性、周期性、异常性特征。
   - 决策生成三类规则。

3. 自动策略数据模型
   - 规则本体复用 `CLUSPolicyRule`。
   - 自动规则分类、置信度、周期槽和 TTL 使用 `CLUSAutoPolicyMeta`。
   - 说明为什么不新增新的通用 `CfgType`。

4. 规则分类算法
   - baseline allow：稳定业务基线。
   - periodic allow：固定时间窗口内出现的正常通信。
   - anomaly deny：启发式异常拒绝。

5. 策略编译与优先级
   - 说明分桶编译。
   - 保持原有 default address table 语义。
   - anomaly deny 高于自动 allow。
   - periodic allow 只在当前时间窗激活。

6. 规则生命周期管理
   - anomaly deny 使用 TTL。
   - baseline / periodic 可根据命中情况老化。
   - 支持人工编辑、删除、多选删除和疑似失效筛选。

### 第 4 章 集群外部暴露面治理与零信任访问控制

建议重点写工程闭环。

推荐小节：

1. Kubernetes 服务暴露面分析
   - Service、NodePort、Ingress、HostPort、LoadBalancer。
   - 暴露面与资源归因。

2. 端口暴露扫描与治理
   - `k8s-port-audit` 扫描 Kubernetes 资源和节点端口。
   - 识别开放端口、所属命名空间、服务、工作负载。
   - 前端页面展示和治理。

3. OpenZiti 零信任接入
   - ziti-controller。
   - ziti-router。
   - identity、service、policy、terminator。
   - 通过零信任路径访问业务服务。

4. 零信任流量与普通流量的区分
   - 普通入口链路可以归为 ingress/direct。
   - OpenZiti 代理链路可以归为 zero_trust。
   - 自动策略学习和展示时应分开归因、分开管控。

注意：

- 不要写“零信任会自动关闭普通入口”，除非实验里确实做了关闭动作。
- 更准确的说法是：系统提供零信任受控入口，并辅助识别仍然存在的直接暴露入口。

### 第 5 章 系统实现

建议按模块写：

- controller 自动策略模块。
- enforcer 流量上报与策略执行复用。
- manager 前端页面。
- 端口暴露治理模块。
- OpenZiti 集成模块。
- 打包与 Kubernetes 部署。

这里可以适当写文件和模块，但不要变成代码流水账。

### 第 6 章 测试与实验

建议至少设计四类实验：

1. baseline allow 实验
   - 例如 `client -> backend` 稳定访问。
   - 观察是否生成基线允许规则。

2. periodic allow 实验
   - 模拟固定时间段访问。
   - 观察是否生成周期允许规则。

3. anomaly deny 实验
   - rogue / nmap 多端口扫描。
   - 观察是否生成异常拒绝规则。

4. 端口暴露与零信任实验
   - 展示直接暴露入口。
   - 发布 OpenZiti 服务。
   - 区分普通入口访问与零信任访问链路。

推荐指标：

- 自动生成规则数量。
- baseline / periodic / anomaly 分类数量。
- any 规则比例。
- 规则命中次数。
- 规则老化数量。
- 策略计算耗时。
- 零信任链路数量。
- 暴露端口数量变化。

### 第 7 章 总结与展望

建议总结：

- 完成了从逐连接即时学习到窗口聚合自动策略生成的改造。
- 实现了基线允许、时间约束允许、异常拒绝三类自动规则。
- 保留了原有策略编译和下发链路，降低了系统侵入性。
- 结合端口暴露治理和零信任访问控制，覆盖了东西向与南北向两个安全维度。

展望可以写：

- 多 controller 场景下的候选态同步。
- 更精细的异常检测模型。
- 更大规模集群下的特征压缩和性能优化。
- 与 Kubernetes NetworkPolicy 的双向转换。
- 更完善的可视化和审计报表。

## 5. 算法表述建议

### baseline allow

建议写成：

> 基线允许规则用于描述长期稳定、重复出现且风险较低的业务通信关系。系统通过连续观察窗口数、历史命中窗口数、观察周期数、源工作负载覆盖率和异常风险反向指标计算稳定性分数。

可使用公式：

```text
S_baseline =
    0.30 * f_consecutive +
    0.25 * f_total +
    0.20 * f_days +
    0.15 * f_srccov +
    0.10 * f_safe
```

不要写成“机器学习白名单算法”。

### periodic allow

建议写成：

> 时间约束允许规则用于描述集中出现在固定时间段内的正常通信行为。系统使用固定时间槽统计流量分布，并通过时间分布熵衡量通信是否集中在少数时间窗口。

可使用公式：

```text
p_i = c_i / Σ c_i
H = - Σ p_i log(p_i)
S_concentration = 1 - H / log(N)
```

其中 `N` 是一周内时间槽总数。

### anomaly deny

建议写成：

> 异常拒绝规则采用启发式威胁行为识别机制，综合新颖性、端口爆发、目标爆发、时间偏离、策略违反和威胁等级等信号生成临时拒绝规则。

可使用公式：

```text
S_anomaly =
    0.25 * f_novelty +
    0.20 * f_portburst +
    0.20 * f_dstburst +
    0.15 * f_time_deviation +
    0.20 * f_violation
```

不要写成“完整机器学习异常检测算法”。

## 6. 当前功能完成度应该怎么写

建议写“已经实现”：

- 自动策略观察入口。
- 连接事件归一化。
- 候选特征窗口聚合。
- baseline / periodic / anomaly 三类评分。
- 自动规则生成与元数据管理。
- 周期规则按时间窗激活。
- anomaly deny TTL。
- 自动规则编辑、删除、多选删除。
- 规则来源筛选。
- 疑似失效规则识别。
- 网络规则页与自动策略页联动。
- 网络活动页自动策略关联查看。
- 端口暴露治理页面。
- OpenZiti 零信任管理入口。
- 打包、部署、镜像更新和集群验证流程。

建议谨慎写“部分实现 / 实验性实现”：

- 大规模生产集群性能。
- 多 controller 候选态同步。
- 复杂机器学习异常检测。
- 完整自动关闭所有直接暴露入口。
- 与 Kubernetes NetworkPolicy 的完整互转。

## 7. 术语统一建议

建议使用：

- 基线允许规则：`baseline allow`
- 时间约束允许规则：`periodic allow`
- 异常拒绝规则：`anomaly deny`
- 自动策略元数据：`auto policy metadata`
- 窗口聚合学习：`window-based aggregation`
- 暴露面治理：`exposure surface governance`
- 零信任访问控制：`zero-trust access control`

不建议在正式贡献点里直接使用：

- 自动白名单。
- 自动黑名单。
- 机器学习异常检测。
- 全新数据面。
- 增量策略计算。

这些词可以在答辩口头解释中作为类比，但论文正文最好用更稳的术语。

可参考：

> 本文围绕 Kubernetes 集群场景下的安全防护需求，设计并实现了一套云主机微隔离系统。针对集群内部东西向通信控制需求，系统基于 MicroSegX/NeuVector 既有控制面、节点代理和数据面链路进行扩展，将原有逐连接即时学习机制改造为基于观察窗口聚合的自动策略生成机制。系统通过稳定性评分、时间周期性分析和启发式威胁行为识别，将观测流量自动分类为基线允许规则、时间约束允许规则和异常拒绝规则，并结合规则元数据、编译优先级和生命周期管理实现策略的自动生成、自动激活和自动回收。针对集群外部南北向访问控制需求，系统引入端口暴露扫描与 OpenZiti 零信任接入能力，实现对开放端口、服务入口和零信任访问路径的统一可视化与治理。实验结果表明，该系统能够在尽量复用原有策略下发链路的前提下，提高微隔离策略生成的自动化程度，并降低直接暴露入口带来的安全风险。

## 10. 写作边界提醒

必须避免过度表述：

- 不要写“本文提出新的底层数据面匹配框架”。
- 不要写“本文实现完整机器学习异常检测算法”。
- 不要写“本文实现了多 controller 高可用候选态同步”。
- 不要写“本文自动消除了所有外部暴露面”。

可以稳妥表述：

- “在既有数据面和策略编译链路基础上进行自动化增强”。
- “采用可解释的启发式评分方法”。
- “第一版特征状态以内存维护，适合实验环境和中小规模验证”。
- “零信任访问控制作为外部暴露面治理的受控入口能力，与端口治理形成配套闭环”。
