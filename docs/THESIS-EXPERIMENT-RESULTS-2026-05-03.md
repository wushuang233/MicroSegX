# 第4章 系统测试与效果评估

本章结合实验过程中的实际现象，对系统改造后的功能效果与实现开销进行分析。本项目没有重新实现 NeuVector 的数据面，也没有替换原有的策略编译和节点侧执行链路，改动主要集中在控制侧的自动规则生成、端口暴露面治理和零信任访问接入。因此，本章重点关注以下问题：内部规则是否能够对应真实业务访问关系，Flask SSTI 靶机被利用后横向访问是否受到限制，外部开放端口是否减少，零信任链路是否能够正常建立，以及新增机制是否破坏原有业务流程。

需要说明的是，本轮实验中，外部暴露面治理与零信任接入部分均采用真实部署和真实访问结果；内部微隔离部分虽然已经能够真实观察到业务流量，但 `web` 命名空间内的自然学习结果尚未完整提升为可执行规则，因此“规则生效效果”部分采用手工创建用户规则的方式模拟学习结果。这里的规则来源属于人工模拟，但流量本身、拦截现象以及命中计数均为真实运行数据。

## 4.1 实验环境

本项目实验环境由 2 台 Ubuntu 主机和 1 台 Windows 客户端组成。两台 Ubuntu 主机构成 Kubernetes 集群，其中 1 台作为控制节点、1 台作为工作节点；Windows 客户端位于集群外部，用于后续人工导入零信任身份并验证受控访问链路。本轮服务端实验结果主要来自 2 台 Ubuntu 主机，Windows 侧不参与自动化执行。

集群内部部署了 Nginx 反向代理、前端服务、后端 API 服务、数据库服务和定时任务服务，同时部署了攻击者 Pod 与 Flask SSTI 漏洞靶机 Pod，用于验证工作负载被利用后的内部访问限制效果。外部访问测试部分部署了 OpenZiti controller、router 和端口暴露面审计模块，用于完成开放端口识别、端口收敛和零信任访问建立。

## 4.2 功能验证

本节主要围绕两部分展开。第一部分验证集群内部通信控制能力，包括稳定业务访问链路保留、漏洞靶机被利用后的横向访问限制以及周期任务通信样本生成；第二部分验证集群外部访问治理能力，包括开放端口识别、业务入口收敛和零信任访问建立。测试目标不是进行大规模性能压测，而是确认第三章设计的主要功能链路能够在当前实验环境中真实运行。

### 4.2.1 内部业务链路与规则对应关系验证

在内部策略生成方面，本轮测试重点不是比较规则数量本身，而是观察规则结果是否能够对应真实业务访问关系。原有逐连接学习方式在发现连接后可以较快生成白名单规则，但这种方式容易把临时访问、调试流量或一次性探测也保留下来。改造后的思路应当是先观察一段时间内的通信行为，再根据访问稳定性、周期性和异常性生成不同类型的规则。

就本轮实验结果而言，集群内部已经能够真实观察到 `nginx -> frontend`、`frontend -> backend`、`backend -> db` 这几条稳定业务链路，但 `web` 命名空间内的自然学习结果尚未完整提升为可执行规则。因此，本节对“规则生效效果”的验证采用手工创建用户规则的方式模拟学习结果；这部分在论文中应当明确标注为“手工模拟学习规则效果验证”。

### 表4.5 稳定业务访问链路验证结果

| 访问链路 | 验证方式 | 实测结果 | 说明 |
|---|---|---|---|

| `frontend -> backend` | 在 `frontend` 容器内访问 `backend` API | 返回 `200` | 前端到后端调用保留 |
| `backend -> db` | 在 `backend` 容器内向 `db` 发送 `PING` | 返回 `PONG` | 后端到数据库依赖保留 |

### 4.2.2 Flask SSTI 靶机场景验证

本实验使用攻击者 Pod 和 Flask SSTI 漏洞靶机 Pod 进行验证。Flask SSTI 靶机用于模拟某个业务工作负载被利用后的情况。本实验不重点讨论漏洞利用细节本身，而是关注靶机在被利用后是否还能继续访问集群内其他无关服务。

首先对靶机本身进行可用性验证，确认其能够正常复现 SSTI。

### 表4.8 Flask SSTI 靶机可用性验证

| 测试 URL | 实测结果 | 说明 |
|---|---|---|
| `http://192.168.198.128:30083/?name={{233*233}}` | 返回 `Hello 54289` | 说明靶机可正常执行 SSTI 表达式 |

随后从“未限制”和“规则生效后”两个阶段比较靶机的内部访问能力。

### 表4.9 Flask SSTI 靶机场景下的访问对比

| 测试阶段 | 访问来源 | 访问目标 | 实测结果 |
|---|---|---|---|
| 微隔离未生效 | `attacker` | `nginx`、`frontend`、`backend`、`db`、`flask-ssti` 等多个目标 | 均可探测到 `OPEN` |

### 4.2.4 外部暴露面识别与端口收敛验证

外部暴露面治理部分的重点是观察业务入口是否从直接端口暴露转向受控接入。相关数据来自 `port-audit` 的治理控制接口和外部暴露面扫描结果。

治理前，`web` 命名空间中共有 7 个业务 NodePort：`30080`、`30081`、`30082`、`30083`、`30084`、`30085`、`30086`。其中 `nginx`、`frontend`、`flask-ssti`、`ftp`、`ssh-demo`、`echo` 在外部扫描中可直接表现为开放目标；`backend` 在本轮扫描中表现为 `timeout`，说明其配置层面仍为公开入口，但运行态扫描结果不同于其他业务端口。

从整个集群节点级开放目标统计来看，`port-audit` 在治理前识别到 25 个开放目标。治理完成并清理临时本机测试监听口后，再结合两台节点的真实监听端口校对，当前治理后全集群对外开放目标数应记为 13 个。若只看 `web` 命名空间的业务入口，则公开业务端口从 7 个降为 0 个；若看全集群公开目标，则收敛前后变化应写成 25 -> 13，而不是 7 -> 0。

## 4.3 效果分析与实现开销讨论

从当前实验结果看，本项目的内部通信控制改造已经能够在不替换底层数据面的前提下，对不同性质的访问进行区分。稳定业务链路可以通过允许规则保留，漏洞利用后的横向访问和异常探测访问可以通过拒绝规则压缩，说明“按业务关系组织规则”的改造方向是成立的。

外部访问治理方面，实验结果表明，端口收敛并不是简单关闭端口，而是把业务入口从多个分散的宿主机端口转移到零信任接入链路中。对管理员而言，这种方式的意义不只是“开放端口数量减少”，而是业务入口从分散暴露转变为集中管理，后续判断某个服务是否仍应对外开放会更清楚。

在实现开销方面，本项目的改动主要集中在控制侧。内部微隔离部分仍然复用 NeuVector 原有连接采集、策略存储、规则编译和节点侧执行链路，没有重写 agent 协议和底层匹配机制。新增工作主要体现在观察窗口维护、连接特征聚合、规则分类与规则元数据管理上。外部访问控制部分新增了端口暴露面审计、资源归因和 OpenZiti 接入展示，但这些工作主要发生在控制和管理流程中，不直接改变业务 Pod 的运行方式。

需要指出的是，本项目没有对大规模集群下的吞吐量、时延和控制器资源占用进行完整压测，因此本章不额外给出未经测试的性能数值。当前能够确认的是，在本轮 2 节点 Ubuntu 集群环境中，内部规则效果验证、端口收敛和零信任接入流程均可以真实运行，且没有破坏正常业务访问。

## 4.5 本章结论

综合本轮实验结果，可以得到以下结论：

1. 在当前 2 节点 Kubernetes 实验环境中，`nginx -> frontend -> backend -> db` 的业务链路能够保持正常通信。
2. 在未限制阶段，攻击者 Pod 可以对 `nginx`、`frontend`、`backend`、`db` 等多个目标发起成功连接，说明业务样本之间确实存在可被利用的横向访问面。
3. 在保护规则生效后，`attacker -> backend`、`attacker -> frontend`、`flask-ssti -> backend`、`flask-ssti -> db` 均出现连接超时，而 `frontend -> backend` 和 `backend -> db` 仍保持成功，说明内部微隔离能够在保留必要业务链路的同时压缩无关横向访问。
4. 在外部治理前，`web` 命名空间存在 7 个公开业务端口；治理后，`web` 命名空间公开业务端口数收敛为 0。若从整个集群节点级开放目标统计来看，开放目标数由 25 个降为 13 个，仅保留 OpenZiti 控制器与路由器以及 Kubernetes 节点必要管理监听口。
5. 在业务端口收敛后，直接访问原 NodePort 已失败，而通过零信任链路仍可访问内部业务页面，说明外部访问方式已经从“直接暴露端口”转变为“基于身份和策略的受控接入”。
